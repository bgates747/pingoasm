# Development log — 2026-07-28

## Outcome

Today established a reproducible performance baseline and a chair-operated
hardware test loop for Pingo 2.15 Alpha 1. The accepted Cube workload renders
at 320×240 with a mean `rendererRender()` time of 231.28 ms, equivalent to
4.32 FPS before display and protocol overhead.

The workflow is now:

```text
edit firmware
  -> build and flash
  -> regenerate/deploy fixture when its profile changes
  -> start listener
  -> press R
  -> Agon resets and autoexec runs benchmark
  -> raw timing log is summarized
```

Hardware remains the performance ground truth. Emulator timings are useful
only for emulator regression.

## Firmware timing instrumentation

`agon-vdp:video/pingo_3d.h` now measures only `rendererRender()`:

1. Hardware uses `esp_timer_get_time()`.
2. The userspace module uses `std::chrono::steady_clock`.
3. Bitmap copying, drawing, flipping, command parsing, and logging are outside
   the measured interval.
4. Hardware uses `force_debug_log()` because ordinary `debug_log()` is compiled
   out of release firmware.
5. Records use the stable form:

   ```text
   PINGO_RENDER seq=0 bmid=1258 render_us=223624
   ```

6. Sequence state is per Pingo control. The target bitmap ID supplies workload
   identity without adding an application-specific VDU command.

The instrumentation is committed on `pingo-codex` as `d66b96d`.

The embedded build uses 42,520 bytes RAM (13.0%) and 1,063,889 bytes flash
(81.2%). Native smoke and ESP32 build/upload passed.

## Profile-driven fixture system

The deterministic benchmark lives outside interactive applications:

```text
benchmarks/render-spin/
├── profiles/
├── fixtures/<profile>/{src,tgt}
└── results/
```

`build_render_benchmark.py` consumes JSON profiles and generates:

1. provenance-marked standalone assembly;
2. a copied, provenance-marked model include;
3. the strict TurboVega helper include;
4. the selected runtime texture; and
5. an assembled `benchmark.bin`.

Cube and HeavyTank profiles prove that model choice is data rather than a new
hand-written application. Profiles control model, texture and format,
dimensions, scale, camera, resolution, warmups, measured frames, rotation axis,
angular step, and reserved IDs.

The Cube workload is fixed at eight warmups plus 36 measured frames, using
absolute Y rotations of 0 through 350 degrees in 10-degree increments. There is
no input polling or frame limiter.

## Robust run identification

An adversarial mixed log exposed why sequence counts alone are insufficient:
after one benchmark, the manually controlled Cube produced an arbitrary number
of additional command-38 renders. A reset also restarted the sequence.

The final scheme reserves:

```text
control ID:              1300
texture bitmap ID:       1256
measured target ID:      1257
warmup target ID:        1258
```

A complete benchmark is identified by eight consecutive warmup target records
followed by 36 measured target records. The summarizer ignores interactive
renders, repeated runs, reset diagnostics, and incomplete runs. Legacy logs
remain readable only when they contain exactly one unambiguous 44-frame run.

## Reconnecting serial listener

`listen_vdp_debug.py` is a standard-library-only serial tee:

1. displays raw VDP traffic in its terminal;
2. appends identical bytes to an explicit or timestamped log;
3. reconnects after USB removal, power cycle, or device loss;
4. takes an exclusive tty lock to prevent corrupt capture;
5. preserves parser-friendly raw logs by keeping status messages terminal-only;
6. restores terminal settings on exit;
7. stops with Ctrl+C; and
8. pulses hardware reset when `R` is pressed.

Real hardware tests confirmed reconnect after a power cycle and reset without
terminating the listener. With SD `autoexec.txt` configured to load and run the
benchmark, pressing `R` produces a complete unattended capture.

The exclusive lock correctly prevents PlatformIO from flashing concurrently.
Stop the listener before upload, then restart it afterward.

## Dual texture implementation

The next working change implements the minimal dual-format path described in
`dual-texture-format-proposal.md`:

1. Pingo command `5` now reads the existing VDP `Bitmap::format` metadata; its
   application-facing payload remains unchanged.
2. RGBA8888 retains the direct four-byte sampling path.
3. RGBA2222 is expanded from `AABBGGRR` to the common Pingo RGBA8888 working
   pixel per sampled texel.
4. No expanded texture copy or conversion buffer is allocated.
5. Unsupported VDP bitmap formats are rejected cleanly.
6. The native test covers all 256 packed bytes, representative RGBA8888 values,
   and UV corner orientation.

The paired `cube-rgba2222` profile changes only the texture file, byte count,
and declared VDP bitmap format relative to `cube-rgba8888`. Both fixtures
assemble to 2,687-byte executables.

Hardware visually qualified both formats. Direct shifts-and-masks expansion
made RGBA2222 3.15% slower than RGBA8888, with two RGBA2222 runs agreeing
within 0.015%. A shared, firmware-resident 256-entry lookup recovered that
cost:

```text
RGBA8888:                   232.631 ms mean, 4.299 FPS
RGBA2222, direct expansion: 239.969 ms mean, 4.167 FPS
RGBA2222, shared lookup:    232.720 ms mean, 4.297 FPS
```

The final RGBA2222 result is within 0.038% of RGBA8888 while using one quarter
of the texture storage and transfer. Pingo allocates no expanded texture copy.
The qualified firmware milestone is `agon-vdp:pingo-codex` commit `b9abe0f`.

Historical `docs/benchmarks/fpscomparisons.txt` measurements also resolved the
remembered larger improvement. Changing the entire Pingo working `Pixel` to
one-byte RGBA2222P reduced the Earth frame from approximately 323–324 ms to
276–277 ms. That older 14.5% frame-time improvement affected framebuffer
clearing and raster writes, not merely sampled texture storage. Restoring a
one-byte working pipeline is intentionally deferred to the next, more invasive
milestone.

## One-byte working and output pipeline (Ultra effort)

The Author explicitly selected Codex's Ultra thinking level for this critical
milestone. The change was constrained to the smallest defensible restoration
of one-byte rendering while retaining the newly qualified dual-input behavior.

The pre-change audit found:

1. Historical commit `14c5779` changed Pingo's working `Pixel` to one-byte
   `AABBGGRR`; that is the change associated with the recorded Earth speedup.
2. Historical direct-render commit `376dd75` hard-coded bitmap `257` and was
   not safe to transplant.
3. The `cube-rgba2222` benchmark used an RGBA2222 source texture but still
   created both render targets as RGBA8888.
4. Command `38` did not validate target format. A one-byte target under the
   old four-byte copy would have caused a fourfold buffer overrun.
5. The clean VDP 2.15 port had lost the established extended bitmap command
   `23,27,&22` used by existing `CTB2` clients.

The qualified implementation makes these bounded changes:

1. Pingo `Pixel` is again exactly one byte, with a compile-time size assertion.
2. RGBA2222 texture sampling is now an identity byte read. RGBA8888 sampling
   retains its real four-byte stride and packs each channel using the VDP's
   documented top-two-bit mapping.
3. The renderer's allocation, clear, and raster writes become one byte per
   pixel through their existing `sizeof(Pixel)` idiom.
4. Command `38` validates target pointer, dimensions, and format. It binds the
   requested RGBA2222 bitmap directly as the render framebuffer. RGBA8888
   targets remain supported by an explicit packed-to-RGBA8888 compatibility
   expansion after the timed renderer interval.
5. VDP bitmap command `&22` was restored from the polished prior implementation
   so existing `CTB2` clients create correctly sized RGBA2222 bitmaps.
6. Benchmark profiles now declare `target_format` independently from
   `texture_format`. The RGBA2222 Cube creates both warmup and measured targets
   with `CTB2`; the RGBA8888 fixtures remain legacy controls.
7. The native pixel/texture test now covers the one-byte invariant, all 256
   packed values, canonical quantization boundaries, RGBA8888 stride, UV row
   direction, and packed target writes.
8. The native VDP smoke renders an empty scene to both RGBA2222 and RGBA8888
   targets.

Verification completed:

1. The Pingo command-surface guard passes.
2. Native unit and dual-target smoke tests pass.
3. A clean embedded build succeeds at 42,520 bytes RAM and 1,064,461 bytes
   flash.
4. Firmware upload to `/dev/ttyUSB0` completed with hash verification.
5. The SD's previously deployed binary—RGBA2222 texture but legacy RGBA8888
   targets—completed exactly 8 warmups and 36 measured frames. This confirms
   that the compatibility output path does not crash or corrupt the run.
6. That preliminary renderer-only run measured 203.729 ms mean, or 4.908 FPS.
   Against the 232.720 ms lookup baseline, frame time fell 12.46% and
   equivalent FPS rose 14.23%.
7. Output expansion remains outside `render_us`, exactly as the earlier bitmap
   copy did, so this result measures the packed renderer rather than end-to-end
   command latency.
8. No emulator files or snapshots were modified.

The regenerated 2,681-byte `cube-rgba2222` executable was subsequently copied
over the same SD path and filename used by the prior fixture:

```text
/mystuff/pingoasm/benchmarks/render-spin/fixtures/cube-rgba2222/tgt/benchmark.bin
```

Its byte stream contains two `CTB2` target-create commands—one warmup and one
measured target—and no RGBA8888 target-create command. Thus the application
uses RGBA2222 for its texture, Pingo working pixels, and rendered output.

The first direct-target capture and a cleared-log repeat agreed within
approximately 1 µs in mean renderer time. The accepted clean run contains

```text

Minimum:              191.603 ms
Median:               202.931 ms
P95:                  213.917 ms
Maximum:              213.955 ms
```

Comparison with qualified earlier hardware runs:

```text

RGBA2222 lookup table:     232.720 ms, 4.297 FPS
```

## External qualified-firmware archive (Light effort)

The Author selected Codex's Light reasoning level for this straightforward
preservation task. Qualified firmware binaries are intentionally kept outside
all project trees and Git history at:

```text
~/Agon/mystuff/pingo-firmware-archive/
```

The initial archive preserves three independently rebuilt, flashable stages:

1. `01-rgba8888-corrected` is the corrected-maths RGBA8888 baseline from
   `agon-vdp` commit `d66b96d`; its qualified Cube result is 231.276 ms and
   4.324 FPS.
2. `02-rgba2222-lookup` is the dual-input, four-byte-working lookup
   implementation from commit `b9abe0f`; its qualified RGBA2222 Cube result is
   232.720 ms and 4.297 FPS.
3. `03-rgba2222-one-byte` is the native one-byte working/output implementation
   from commit `a382ede`; its qualified Cube result is 203.626 ms and
   4.911 FPS.

Each stage contains `firmware.bin`, `firmware.sha256`, `manifest.json`, and its
captured PlatformIO `build.log`. Manifests record the full source commit,
PlatformIO 6.1.19, `espressif32@6.6.0`, the resolved `vdp-gl` commit, supported
texture/target formats, binary size and checksum, and the associated benchmark.

All three per-stage checksums and the aggregate `SHA256SUMS` file pass.
`esptool.py --chip esp32 image_info` also reports valid image checksums and
validation hashes for all three binaries.

The external `rebuild_archive.sh` exports source commits into temporary
directories and never changes either project working tree. Existing binaries
are immutable by default: a normal invocation verifies and preserves them.
Replacement requires the explicit `--force` option because ESP32 builds embed
build metadata and may not reproduce an earlier binary SHA even from identical
source.

The archive is therefore the canonical source of exact regression-test
binaries; the cited Git commits remain the canonical source code.

## Earth fixtures and chained hardware suites

EarthIco and EarthUV were added to the deterministic render-spin benchmarks in
both corrected-RGBA8888 and one-byte-RGBA2222 forms. Their authoritative Blend
files were freshly exported to temporary OBJ files with Blender 4.0.2 before
conversion. Vertex, UV, normal, winding, and ordered face-corner comparisons
confirmed the checked-in OBJs are correct; they were preserved rather than
replaced merely to adopt a newer exporter's textual conventions.

The benchmark builder now accepts OBJ and PNG sources directly in a profile,
generates a provenance-marked portable `model.inc`, converts the selected
texture format, and assembles the fixture. All four Earth fixture builds are
deterministic. A dependency-free `obj_bounds.py` utility reports independent
OBJ minima, maxima, spans, and centers in text or JSON form.

The isolated current-Pingo emulator snapshot was refreshed from qualified
`agon-vdp:pingo-codex` commit `a382ede`. EarthIco and EarthUV both rendered
correctly there with RGBA2222 textures. The emulator's private `autoexec.txt`
was used only for fixture selection and remains untracked, preserving the
requirement for human validation before emulator commits.

An initial 720×360 RGBA8888 EarthUV fixture produced a partial globe, missing
texture, and a noisy equatorial band on hardware. This was diagnosed as client
memory corruption: the helper stages the complete 1,036,800-byte texture in
eZ80 RAM, while an application at `0x40000` has approximately 512 KiB through
MOS's `0xBFFFF` RAM limit. Both EarthUV formats were therefore regenerated from
the same established 320×160 source image. The resulting 204,800-byte RGBA8888
and 51,200-byte RGBA2222 payloads fit and rendered correctly.

Hardware `autoexec.txt` successfully chained EarthIco and EarthUV with
synchronous `cd`, `load`, and `run` commands. Five cold-reset suites were
captured for the corrected RGBA8888 firmware and five for the current one-byte
firmware, producing 180 measured frames in every model/pipeline cell.

## Combined Cube and Earth hardware comparison

The corrected RGBA8888 firmware and current one-byte RGBA2222 firmware were
compared with the same deterministic protocol: eight warmups followed by 36
measured absolute 10-degree Y rotations. The timer covers `rendererRender()`
only.

| Model | RGBA8888 corrected | RGBA2222 one-byte | FPS gain |
|---|---:|---:|---:|
| Cube | 231.276 ms / 4.324 FPS | 203.626 ms / 4.911 FPS | 13.58% |
| EarthIco | 118.895 ms / 8.411 FPS | 97.225 ms / 10.285 FPS | 22.29% |
| EarthUV | 174.488 ms / 5.731 FPS | 145.788 ms / 6.859 FPS | 19.69% |

The corresponding frame-time reductions are 11.96% for Cube, 18.23% for
EarthIco, and 16.45% for EarthUV.

Cube uses its established labeled 34×34 texture and the previously qualified
single clean capture for each firmware. The Earth results aggregate five
hardware runs per firmware—180 measured frames in each model/pipeline cell.
EarthIco has 12 vertices and 20 triangles; EarthUV has 482 vertices and 960
triangles. Both Earth formats use corresponding source pixels, and EarthUV
uses the same 320×160 source image in each pipeline.

The one-byte renderer therefore improves all three tested workloads. The gain
persists under EarthUV's much greater transform and triangle-setup load rather
than being confined to Cube or another low-poly case.

The complete Earth report is
`benchmarks/render-spin/results/earth-suite-hardware-2026-07-28.md`. Cube's
structured controls are
`benchmarks/render-spin/results/cube-rgba8888-hardware-2026-07-28.json` and
`benchmarks/render-spin/results/cube-rgba2222-one-byte-hardware-2026-07-28.json`.
