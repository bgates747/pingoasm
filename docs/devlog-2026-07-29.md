### Polar elliptical camera orbit

A separate fixture then exercised camera translation and rotation together.
Earth is one focus of an ellipse in the world Y-Z plane. The camera:

1. starts at `(0,0,10000)`, 11,000 units from Earth;
2. sweeps at constant angle rather than simulated orbital velocity;
3. passes over the north pole;
4. reaches periapsis 2,500 units beyond Earth's far side at `(0,0,-3500)`;
5. passes over the south pole; and
6. returns exactly to its starting position and orientation.

The radius is generated from:

```text
a = (apoapsis + periapsis) / 2
e = (apoapsis - periapsis) / (apoapsis + periapsis)
p = a(1 - e²)
r = p / (1 - e cos(theta))
```

The angular sweep is deliberately uniform; this is geometric test motion, not
Keplerian orbital mechanics. The camera completes one ellipse while the
objects complete two orbits.

An unrotated camera faces local `-Z`. On this polar path, a continuous X
rotation from 0 through -360 degrees always points that axis toward Earth.
Camera Y rotation and local roll remain zero. This choice is both simple and
important: at the polar crossings, camera-forward is parallel to the usual
world-up vector. A conventional `lookAt(position, target, world_up)` is
singular there. Prescribing the continuous X angle chooses the roll frame by
continuity while deliberately traversing the +/-90-degree pitch conditions
associated with Euler gimbal lock.

The TV-compatible assembly helper did not previously expose the absolute
three-axis camera-rotation command. `scrabs` was added using Pingo subcommand
21; an older helper elsewhere incorrectly labels a three-axis payload as
subcommand 18, which accepts only one X angle and must not be copied.

Eleven generator and mathematical regression tests now cover the canonical
orbit, camera dolly, elliptical endpoints, polar crossing, camera angles,
object motion, exact closure, validation, and eZ80 staging-memory bound. The
polar fixture assembled successfully and passed visual review in both the
qualified emulator and physical hardware. This establishes camera pose
translation and rotation—including smooth passage through both poles—as
working for this renderer state.

## Selective modern-upstream optimization sweep

The Author granted a free hand under Ultra reasoning to extract useful work
from modern `fededevi/pingo` before pursuing less attributable renderer
experiments. The principal risk was confirmed: modern upstream is not a
drop-in library update. Its `Entity`/callback object model, transform
ownership, camera inversion, mesh UV ownership, and backend interfaces have
diverged substantially from the TurboVega-era code retained by Agon. The
object-model rewrite was therefore treated as context, not as a merge target.

### Silent emulator benchmark control

The owned Fab fork now has `scripts/benchmark-pingo.py`, a strict headless
runner that uses dummy SDL video and audio drivers. It opens no window and
plays no boot beep. Each repeat starts a fresh emulator process with an
explicit VDP module, MOS image, simulated SD card, software renderer,
zero-initialized RAM, and unlimited eZ80 execution.

The harness requires:

1. one active `LOAD` followed by one active `RUN` in `autoexec.txt`;
2. an existing selected executable while preserving the established
   project-local SD symlink convention;
3. contiguous `PINGO_RENDER` sequence numbers and declared bitmap IDs/counts;
4. stable SHA-256 identities for all benchmark inputs and the harness itself;
5. clean debugger-assisted shutdown; and
6. staged publication, with the JSON report written last so a failed forced
   rerun cannot pair stale metadata with partial or replaced logs.

The installed emulator helper suite now has 28 passing tests. A complete
289-frame silent integration run also passed. Emulator timing is suitable for
same-host candidate screening only; ESP32 hardware remains the performance
and final visual authority.

### Accepted upstream-derived changes

Three deliberately small changes survived isolation:

1. `vec3Normalize` adopts the guarded scalar method from upstream
   `fb67d951c4f05ca5fa04c45dcb3cb3b02f861163`: zero and exact-unit fast
   paths, one square root, one reciprocal, and three multiplies instead of
   three divisions.
2. `mat4Inverse` adopts the same commit's exact translation-only fast path,
   which also covers identity. Upstream's separate identity predicate was
   removed as redundant, and its scale-only path was rejected because it
   takes unguarded reciprocals of scale components.
3. View and projection are composed once per object and applied with one
   matrix-vector product per triangle vertex. This is a locally derived
   VP-only adaptation inspired by upstream transform-composition lineage,
   notably `a0ed0cb`; it is not a literal port. It preserves the Agon port's
   model-space lighting, camera-pose contract, and older object model.

The composed call relies on the established, counterintuitive contract that
`mat4MultiplyM(m1, m2)` returns `m2 × m1`; therefore
`mat4MultiplyM(&view, &projection)` correctly produces
`projection × view`.

A new native math test covers zero/unit/general normalization, identity,
translation-only and rotated general inverses, and a nontrivial
sequential-versus-composed view/projection transform. Ordinary and diagnostic
native suites pass. Both embedded PlatformIO builds also pass: ordinary
firmware uses 1,065,125 bytes of flash, and the diagnostic variant uses
1,067,385 bytes.

### Rejected upstream candidates

Measured isolation prevented several superficially attractive imports:

1. changing the affine matrix-vector helper to consume arbitrary input `w`
   slowed the ellipse fixture by 15.72%; current pre-projection inputs
   intentionally have `w=1`;
2. broad upstream raster cleanup slowed it by 3.47%, and a narrower cleanup
   slowed it by 2.30%;
3. upstream identity and translation special cases in general matrix
   multiplication added comparison overhead and no useful whole-frame gain;
4. moving VP composition from once per object to once per renderer invocation
   showed no repeatable benefit and added state; and
5. the `Entity` refactor, renderer-side camera inversion, scale-only inverse,
   singular-inverse behavior, hard-coded far distance, and composition inside
   the triangle loop were rejected on semantic or safety grounds.

The float-literal experiment remains open for eventual ESP32 measurement:
native/emulator results do not settle the cost of the embedded
double-precision helper calls seen in disassembly.

## Cached object-AABB candidate: accepted hardware result

The authorized object-level culling candidate is now ready for physical
review. Every mesh caches a finite model-space AABB after a complete vertex
upload. For each eligible object, the renderer transforms the eight box
corners and rejects the object only when every corner lies outside one common
clip plane. Missing, malformed, non-finite, or unordered bounds fail open.
The existing triangle frustum and backface paths remain unchanged for retained
objects.

Closed diagnostic schema 3 adds bounds-tested objects (`obt`),
object-frustum rejections (`ofr`), and indexed triangle triplets avoided
(`ta`). Across one diagnostic pass of each 289-frame selected scene:
