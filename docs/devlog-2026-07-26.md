# Development log: 2026-07-26

Today converted the recovered Pingo work from a collection of experiments into
a reproducible development setup spanning real Agon hardware, the VDP firmware,
the Fab Agon emulator, and the assembly sample applications.

## Recovery and validation

- Reconstructed the project's history and recorded the current state, open
  questions, and the relationship between the original `fededevi/pingo`,
  TurboVega's `pingo3D` port, and this VDP branch.
- Installed and repaired the PlatformIO/CMake development environment, including
  the local Python environment, serial-device permissions, build exclusions, and
  editor configuration.
- Built and flashed the Pingo VDP firmware to real hardware.
- Confirmed that ordinary VDP software still works and that the recovered Pingo
  samples run on hardware.
- Tested the camera and object movement samples. The remembered near-camera
  distortion was not present in the current firmware.

## Emulator workflow

- Investigated Fab Agon Emulator's firmware-loading path and established that an
  external VDP module can be injected without rebuilding the whole emulator.
- Created an owned Fab Agon Emulator fork and a `pingo` branch, while preserving
  the pristine upstream clone separately.
- Added scripts for synchronizing a newly built VDP module into the emulator,
  checking the active Pingo components, and launching reproducible tests.
- Added a project-local emulator profile under `pingoasm/emulator`, isolated from
  the standard emulator profiles.
- Validated the reorganized `moveobj/tri` sample with the emulator's headless
  framebuffer oracle.
- Changed emulator deployment to replace the simulated SD contents with a full
  snapshot of `apps/` at `/mystuff/pingoasm/apps`.
- Made `autoexec.txt` user-controlled: deployment and profile-refresh scripts
  preserve it byte-for-byte. The current local profile loads, but does not run,
  `/mystuff/pingoasm/apps/moveair/tgt/jet.bin`.

## Assembly application reorganization

- Replaced the old intermingled source-and-target layout with top-level
  `apps/<mode>/src` and ignored `apps/<mode>/tgt` directories.
- Moved shared assembly material to `apps/_common` so it sorts prominently and
  remains distinct from runnable applications.
- Kept every generated `.asm` and `.inc` file in the consuming application's
  `src` directory for portability.
- Added conspicuous generated-file headers identifying the generator and source.
- Archived obsolete duplicated sample trees instead of silently discarding
  potentially useful historical material.
- Added a Python build driver that composes common application code with
  model-specific assembly and assets, then builds all eleven recovered samples.
- Kept hardware deployment deliberately narrower: it replaces only the selected
  application's `tgt` directory on the mounted SD card.
- Documented the recovered mini-linker/build process, the new directory
  convention, emulator deployment, rendering tools, and deferred model cleanup.

## TODO: design the Blender-to-application asset pipeline

Design a sane, traceable workflow from a Blender source file to a finalized
assembly application and its texture binaries.

The `.blend` file and original texture assets—usually PNG images—should live as
close as practical to the sample application that consumes them. Shared models
and textures must not be duplicated merely to force locality, so the design also
needs an explicit shared-assets convention and machine-readable provenance from
each application back to every Blender file and original texture it uses.

The next pass should decide:

- where application-local `.blend` files and PNG sources live;
- where genuinely shared models and textures live;
- how an application declares those dependencies;
- which files are authoritative sources versus generated intermediates;
- how Blender export, model-to-assembly conversion, texture conversion,
  assembly, and packaging become one reproducible command; and
- how generated `.asm`, `.inc`, `.rgba2`, and final binaries record or expose
  their provenance without sacrificing the portability of an application's
  `src` and `tgt` directories.
