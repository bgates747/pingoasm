# Assembly build and application pipeline

This document records the current application build, its historical purpose,
and the remaining limitations.

The build entry point is:

```text
build/scripts/build_samples.py
```

## Current application contract

Applications are top-level project resources:

```text
apps/
    _common/
    moveair/
        src/
        tgt/
    movecam/
        src/
        tgt/
    movefsim/
        src/
        tgt/
    moveobj/
        src/
        tgt/
    wolf/
        src/
        tgt/
```

For every application:

- `src/` is flat and contains only `.asm` and `.inc`;
- `tgt/` is flat and contains only `.bin` and `.rgba2`;
- `src/` is tracked;
- `tgt/` is ignored;
- the complete `tgt/` is the runtime payload copied to an SD card.

`apps/_common` sorts first deliberately. Its leading underscore means that it
is shared build material, not a deployable application. Application discovery
must still validate the presence of `src/` and `tgt/` rather than relying only
on the name.

## Generated source policy

Generated assembly remains in the relevant app's `src/` so the application
source is inspectable, portable, and can be copied elsewhere for manual
experimentation.

Every generated `.asm` and `.inc` begins with:

```asm
; =============================================================================
; AUTO-GENERATED FILE - DO NOT EDIT
; Generated by: build/scripts/build_samples.py
; Generated from: <repository-relative authoritative input>
; Edit the generator or its authoritative inputs instead.
; =============================================================================
```

This warning applies to the copy inside an automatically generated app.
Someone may copy that source directory elsewhere and edit it manually; rerunning
the build intentionally replaces the generated app's own `src/`.

Common dependencies needed by a generated application are copied from
`apps/_common` into its `src/`. The generated source therefore does not depend
on reaching outside its own directory during assembly.

Assembly-producing asset scripts must follow the same banner convention.
`build/scripts/blender_obj_to_asm.py` now identifies itself in files it writes.
Existing model includes will receive a provenance audit during the model
layout work.

## Authoritative inputs

### Shared assembly

`apps/_common` contains:

```text
model_viewer.asm
input.inc
inputair.inc
inputcam.inc
inputobj.inc
timer.inc
vdu_pingo.inc
```

`model_viewer.asm` uses comment-delimited blocks as its small build manifest:

- `application includes`: common dependencies copied into generated source;
- `control includes`: mutually exclusive input implementations;
- `model includes`: generic models actively built;
- `placeholder includes`: models not built by the generic harness.

The active generic models are:

```text
jet.inc
cube.inc
earthuv.inc
tri.inc
```

`koak28lr.inc` is intentionally a placeholder. It exposes specialized
`koak28lr_*` symbols rather than the generic `model_*` interface and belongs to
the flight applications, not the generic viewer matrix.

### Temporary model library

`src/asm/models` currently contains model includes and texture assets. For
example, `cube.inc` names:

```asm
model_texture: db "blenderaxes.rgba2",0
```

The builder copies the model include into generated `src/`, discovers the
quoted texture dependency, and copies the texture into `tgt/`.

This model library is intentionally the next restructuring target. See
[Model and asset reorganization TODO](model-asset-reorganization-todo.md).

## Generated applications

The builder creates the Cartesian product:

```text
movecam, moveobj
    x
jet, cube, earthuv, tri
```

For example:

```text
apps/moveobj/
    src/
        cube.asm
        cube.inc
        input.inc
        inputobj.inc
        timer.inc
        vdu_pingo.inc
        ...other generated model entry points and includes
    tgt/
        cube.bin
        blenderaxes.rgba2
        ...other binaries and textures
```

The `.asm` selects one control implementation and one model. The source
directory contains all includes required by `ez80asm`; MOS needs only the
binary and runtime textures in `tgt/`.

## Specialized applications

These applications have authoritative, hand-developed source:

```text
apps/moveair/src/jet.asm
apps/movefsim/src/fsim.asm
apps/wolf/src/wolf.asm
```

The same build command assembles them into their corresponding `tgt/`
directories without regenerating their source.

Wolf previously requested a missing `wolf_tex.rgba8`. During the flat-layout
migration it was changed to use the existing 160x160 `wolf_tex.rgba2`, with
the matching file type and 25,600-byte size.

## Build operation

From any working directory:

```bash
~/Agon/mystuff/pingoasm/.venv/bin/python \
  ~/Agon/mystuff/pingoasm/build/scripts/build_samples.py
```

The script resolves the project root from its own path. It:

1. replaces `apps/movecam/src`, `apps/movecam/tgt`,
   `apps/moveobj/src`, and `apps/moveobj/tgt`;
2. copies and banners required common and model includes;
3. generates and banners one top-level assembly file per model/mode;
4. copies each discovered RGBA2 texture into the app target;
5. invokes `ez80asm` from the app source directory;
6. rebuilds `moveair`, `movefsim`, and `wolf`;
7. propagates any assembler failure as a nonzero process result;
8. prints the complete output list.

The current successful build produces eleven binaries:

```text
apps/movecam/tgt/{jet,cube,earthuv,tri}.bin
apps/moveobj/tgt/{jet,cube,earthuv,tri}.bin
apps/moveair/tgt/jet.bin
apps/movefsim/tgt/fsim.bin
apps/wolf/tgt/wolf.bin
```

The macro parameters in all active `vdu_pingo.inc` files use unambiguous names
such as `VERTEX_DATA`, `VERTEX_COUNT`, `MESH_ID`, and `BITMAP_ID`. This avoids
the installed `ez80asm` 2.1 replacing shorter parameter names inside longer
identifiers.

## Deployment

For emulator deployment, `build/scripts/deploy.py` completely clears the
project-local emulated SD card and copies:

```text
apps/
```

to:

```text
/mystuff/pingoasm/apps/
```

It preserves the user-controlled `autoexec.txt` unchanged. The current local
emulator configuration loads:

```text
/mystuff/pingoasm/apps/moveair/tgt/jet.bin
```

The emulator SD contains only the preserved `autoexec.txt` and the copied Pingo
application tree. Hardware deployment remains narrower: it replaces one selected
`apps/<app>/tgt` at the matching hardware SD path.

The deployed cube was verified byte-identical to the newly built local target.
The obsolete `/mystuff/pingoasm/samples/moveobj` emulator path was removed.

## Verification

The flat application migration passed:

- Python bytecode compilation for the build and deployment entry points;
- one complete 11-binary build;
- extension checks proving app `src/` contains only `.asm`/`.inc`;
- extension checks proving app `tgt/` contains only `.bin`/`.rgba2`;
- generated-file banner checks across both generated source trees;
- emulator profile regeneration and deployment at the new mirrored path;
- SHA-256 equality between local and deployed `moveobj/cube.bin`.
- the owned Fab headless `moveobj/tri` regression, producing the accepted
  76,800-byte target hash
  `f81dd66876ef012a6f1e52bae2821c275f1cf33e9a7e977c193be93bad4b4958`.

The rebuilt binaries for `moveobj/cube`, `movecam/jet`, `moveair/jet`, and

## Remaining build-tool limitations

The build now works, but modernization is not complete:

- the generic app and model lists are still constants/marked blocks rather
  than explicit metadata;
- texture discovery still parses `_texture: db` lines;
- generated app directories are replaced non-atomically;
- there is no selective app/model command-line interface;
- specialized runtime-asset production is not yet automated;
- there is no tracked release/export packaging step.

The planned deployment/release directory will eventually contain tracked ZIP
packages with both `src/` and `tgt/`. That is deliberately outside this
structural pass.

## Historical development

The original script was introduced as
`src/asm/template/do_assembly.py` in commit `fdd1b43` on August 16, 2024. It
generated camera-control and object-control programs by combining a common
application, one control include, and each enabled model.

Initially it copied the entire historical `src/asm/build` directory into every
target. Commit `5d3d716` on September 11 changed it to copy only the selected
model and referenced texture, producing smaller self-contained packages.

The script later generated `moveair` and special flight-simulator images.
Commit `4d14d30` on October 24 commented out that path after the flight work
diverged into specialized `moveair` and `movefsim` applications.

The old convention deliberately mixed source, copied dependencies, textures,
and binaries so one directory could be zipped for Discord or copied directly
to an SD card. The current structure preserves that portability while making
the boundary explicit: portable assembly is in `src/`, and the exact runtime
payload is in `tgt/`.
