# Development log: 2026-07-27

Today established a trustworthy historical baseline for the Pingo project.
The master project spans `pingoasm`, the owned `agon-vdp` fork, and the owned
Fab Agon Emulator fork, but this log lives in `pingoasm` as the durable
cross-repository record.

## Reconstructing the research agenda

1. Identified `movecam` and `moveobj` as the canonical minimal test modes.
   Each contains one object and changes either the camera or the object, never
   both, so transform failures can be isolated.
2. Kept `moveair` and `movefsim` as examples of behavior wanted by fuller
   applications, but deferred their design questions until the core renderer
   is understood.
3. Recorded that `wolf` was an early suitability experiment for a maze-like
   shooter. The current renderer is not fast enough, although that assessment
   could change if later optimization work succeeds.
4. Clarified the original performance target: improve the spinning globe at
   320×240 from roughly 3 FPS to at least 15 FPS on the dual-core 240 MHz
   ESP32.
5. Preserved reference copies of the `hecker` and `hecker2` optimization work
   outside the active firmware branches so the code can be inspected without
   repeatedly checking out those branches.
6. Recorded that development originally stopped because the attempted Hecker
   optimizations rendered garbage.
7. Elevated a clean reconstruction of TurboVega's port to the highest-priority
   task. The intent is to begin from an understood historical implementation
   before reintroducing fixes or optimizations.

## Canonical visual fixtures

1. Defined the cube as the simplest complete regression fixture. Its texture
   assigns a distinct color and an unambiguous `+X`, `-X`, `+Y`, `-Y`, `+Z`,
   or `-Z` label to every face, with decorations that expose mirroring.
2. Retained HeavyTank because it is chiral about all three axes. It exposes
   compounded transform, winding, mirroring, and orientation failures that
   symmetric triangle and cube geometry can hide.
3. Built strict TurboVega-compatible move-object fixtures for triangle, cube,
   and HeavyTank. They use only TurboVega's commands `0` through `40` and use
   RGBA8888 textures.
4. Moved the durable fixture sources into `apps/turbovega/src`; generated
   binaries and textures remain in the ignored `apps/turbovega/tgt`.
5. Created a user-run SD-card copy helper because the execution environment
   cannot reliably observe removable-media mounts. Pop!_OS was also configured
   to automount cards inserted through the USB-hub SD reader.
6. Verified that the strict fixtures run on TurboVega's exact final firmware.
   Triangle and cube expose affine rather than perspective-correct texture
   interpolation. HeavyTank additionally exposes the historical orientation
   and apparent inside-out behavior.
7. Confirmed that TurboVega's own `teapot.bas` and `orientation.bas` fixtures
   run on his final firmware, but do not exercise enough of the pipeline to
   reveal all faults exposed by HeavyTank.
8. Used Jukebox repeatedly as a non-Pingo smoke test. Successful playback
   showed that failed Pingo tests had not fundamentally broken ordinary VDP
   operation.

## Incorrect newer-Pingo experiment

1. The first construction of `tv-port` mistakenly combined VDP 2.15 with the
   latest `fededevi/pingo` internals while adapting TurboVega's wire protocol
   around them.
2. The strict fixtures initially cleared the output bitmap to light blue but
   rendered no geometry. They exited cleanly, and Jukebox still worked.
3. Source comparison found that newer Pingo treats `Renderer.camera_view` as a
   camera pose and inverts it inside object rendering. TurboVega's bridge
   supplies the already-final view transform. With the fixture's Z translation
   of `-25`, the extra inversion placed all geometry behind the camera.
4. A compatibility inversion made the geometry visible, proving that diagnosis,
   but the models appeared much farther away and object rotation behaved as
   though it orbited the scene origin.
5. Those additional failures demonstrated broader transform-semantic drift.
   Patching newer Pingo to imitate TurboVega would not produce a trustworthy
   historical baseline, so the experiment was abandoned rather than extended.

## Hardware observations at this baseline

1. The perspective texture-mapping defect persists, as expected. It has not
   been fixed.
2. The cube fixture sends a camera-translation command of `(0, 0, -25)` in
   1/128-unit fixed point. TurboVega places the resulting matrix directly in
   `renderer.camera_view`, so it transforms the world origin to view-space
   Z = -25. The command value must not be mistaken for the camera's world-space
   position.
3. Under the conventional inverse-view interpretation, that matrix corresponds
   to a camera at world Z = +25 looking toward the origin along negative Z. One
   would consequently expect the cube's `+Z` face to face the camera, yet the
   visible face is labeled `-Z` and reads upright. This discrepancy is evidence
   within the orientation/geometry/UV problem, not a settled handedness
   convention.
4. Rotating the cube to expose its top shows `+X`; the expected face is `+Y`.
5. The bottom shows `-X`; the expected face is `-Y`.
6. The screen-right side shows `-Y`; the expected face is `+X`.
7. The screen-left side shows `+Y`; the expected face is `-X`.
8. Translation keys otherwise move the object as expected.
9. Rotation controls otherwise respond in the expected directions.
10. Page Up moves the model downward and Page Down moves it upward. This is the
    characteristic symptom of the model being rendered upside down.
11. The upright `-Z` face label initially appears to conflict with the
    upside-down geometry symptom. That observation is intentionally preserved:
    geometry orientation, UV orientation, texture image row order, and screen
    coordinates may contain compensating errors and must be tested separately.

## Next work

Use this committed VDP 2.15 plus TurboVega-final baseline to isolate pipeline
faults one at a time. Do not introduce the newer upstream Pingo renderer or the
later local extensions while diagnosing the historical transform, orientation,
winding, and texture-projection behavior.

The active reconstruction work will proceed on a new `pingo-codex` branch in
the owned `agon-vdp` fork. That branch will begin at the exact committed and
published tip of `tv-port`. The `tv-port` branch remains the immutable,
hardware-qualified historical control; `pingo-codex` is where Codex-assisted
tests, corrections, and deliberately selected upstream ideas will be developed
one attributable change at a time.
