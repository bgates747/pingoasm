## Coordinate and image conventions

1. The world is right-handed: `+X` right, `+Y` up, `+Z` toward the viewer.
2. An unrotated object or camera faces `-Z`.
3. VDU camera translation and rotation describe a pose, exactly like object
   transforms.
4. A camera at `(0, 0, +25)` sees an object at the origin; the bridge inverts
   that pose exactly once to obtain the view matrix.
5. World and NDC `+Y` point up. Render-target memory is top-origin with `+Y`
   down, so viewport conversion reflects Y exactly once.
6. UVs follow Blender/OBJ convention (`v=0` at the bottom). RGBA data is
   top-row first, so the sampler performs the sole V-to-image-row conversion.
7. Pingo's existing row-major matrices, column-vector use, and multiplication
   behavior remain in place pending focused numerical tests.

> stupid convention needs to be dragged out back and shot.”

## Attributable renderer corrections

### 1. Camera pose to view matrix

The VDU bridge now inverts the camera pose once before assigning
`renderer.camera_view`. Hardware confirmed that the canonical `+25` camera
fixture sees the cube again.

### 2. Viewport Y and rasterizer signs

Viewport conversion reflects Y into top-origin target coordinates. Because
that reflection reverses screen-space winding, the rasterizer accepts edge
weights matching the triangle area's sign. Hardware confirmed correct visual
directions for all X/Y/Z translations and rotations.

### 3. Texture-row orientation

`texture_readF()` clamps normalized coordinates, maps U over `width - 1`, maps
`1-v` over `height - 1`, and uses the actual texture height. All labeled cube
faces now select the correct texture region and rotate into view upright.

### 4. Perspective-correct UV interpolation

The renderer retains reciprocal clip-space W at each vertex, interpolates
`u/w`, `v/w`, and `1/w`, then reconstructs U and V per pixel. This replaces
the historical depth-based interpolation. Cube perspective is now visually
correct on hardware and emulator.

The camera, viewport, sampler, and interpolation changes were deliberately
separated so compensating errors could not conceal one another. The viewport
and texture stages were performed with Codex's “Light” reasoning setting, as
requested for effort comparison.

## Movement ownership and local-axis deltas

The later extended firmware introduced local-axis transform deltas so a car,
aircraft, or camera could move relative to its current orientation. The
high-bit command family mirrored the absolute commands:

1. `141 = 13 + 128`: object rotation delta.
2. `145 = 17 + 128`: object translation delta.
3. `149 = 21 + 128`: camera rotation delta.
4. `153 = 25 + 128`: camera translation delta.

For objects, the effective composition was:

```text
new_transform = current_transform × local_delta
```

Thus local `-Z` followed an object's nose. The concept and command numbering
were reasonable, but the implementation mixed two representations of one pose:

1. Absolute scale/Euler/translation fields could become stale after matrix
   deltas accumulated.
2. A later absolute update rebuilt the matrix from those stale fields and
   could erase local movement history.
3. Each delta matrix incorrectly began with the object's scale rather than
   identity, potentially applying scale repeatedly.
4. Object and camera paths reversed multiplication arguments differently
   because camera/view semantics were still confused.
5. `mat4MultiplyM(m1, m2)` returns `m2 × m1`, making otherwise valid
   composition exceptionally difficult to audit.
6. “Relative” (add a delta) and “local” (interpret it in rotated object axes)
   were treated as one concept even though world-relative and local-relative
   operations are independently useful.

Modern upstream Pingo does not provide a movement system. It gives each
`Entity` a transform matrix and composes parent/child transforms during
rendering; the embedding application still creates and updates the pose.

The strict TV-compatible applications already follow the preferable ownership
model. They accumulate position and Euler angles in assembly, then send the
resulting absolute pose with commands `13` and `17`. The firmware stores the
latest values and rebuilds the render transform; it does not perform gameplay
movement.

### Decision: the application owns authoritative movement

The VDP connection is effectively write-only. A game must know positions for
collisions, triggers, AI, physics, saves, and branching, but cannot recover a
VDP-accumulated pose. Computing movement independently in both places would
create two versions of the world and invite drift through rounding, ordering,
or lost commands.

Therefore:

1. The application owns authoritative position, orientation, scale, movement,
   collision, and game rules.
2. The VDP retains only the last absolute pose needed for rendering.
3. Object and camera commands continue to set absolute poses.
4. Local-axis movement is calculated once in client support code:

   ```text
   world_delta = orientation × local_delta
   position += world_delta
   ```

5. The application performs gameplay checks, then sends the resulting absolute
   translation and rotation to the VDP.
6. Reusable `pingoasm` routines should eventually provide operations such as
   `translate_pose_local`, `rotate_pose_local`, and `send_pose_to_vdp`.
7. The high-bit firmware delta commands should not return merely as gameplay
   conveniences. They should be reconsidered only if a distinct,
   rendering-only use is demonstrated.

This division avoids duplicate arithmetic and hidden renderer state, permits a
complete pose to repair synchronization after a bad command, and ensures save
games, replays, collisions, hardware, and emulator all consume the same
authoritative simulation state.
